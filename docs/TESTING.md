# Тестирование (ТЗ §26)

## Как запускать

```bash
npm test                          # unit (shared + движок) и integration (API) — нужна БД booking_test
npm run test:e2e                  # Playwright — нужны запущенные API, worker и web с демо-данными
npm run lint && npm run typecheck
node apps/api/scripts/load-test.mjs http://localhost:4000 --concurrency 8   # нагрузочный (на тестовом стенде!)
```

## Конкурентные проверки (§26.4)

| Сценарий | Результат |
|---|---|
| 10 клиентов одновременно на одного специалиста и время | 1 резерв, 9 × `409 SLOT_UNAVAILABLE` |
| 2 клиента, разные специалисты, один кабинет | 1 резерв |
| Параллельное назначение «любого» специалиста (4 запроса, 2 мастера) | 2 резерва у разных мастеров, 2 отказа |

| Повторный запрос создания (Idempotency-Key) | тот же ответ, 1 запись |
| Повторная доставка уведомления / двойной drain / повтор webhook | 1 сообщение, 1 статус |
| Нагрузка: 40 одновременных попыток на один слот | ровно 1 успех, 39 конфликтов |
| Параллельное создание филиалов сверх лимита | лимит не превышен |

## Нагрузочное тестирование (§23)

Ноутбук разработчика (Windows 11, 1 процесс API, PostgreSQL на той же машине), демо-филиал, прогрев процесса — первый прогон после запуска. Прогон 2026-11-21:

| Сценарий | Параллельность | RPS | p50 | p95 | Цель |
|---|---|---|---|---|---|
| Получение слотов | 8 | 152–161 | 49–52 мс | 55–61 мс | ≤ 150 мс при 100 RPS ✅ |
| Получение слотов (19.11) | 25 | 122–129 | 188 мс | 217–300 мс | очередь на одном процессе ⚠️ |
| Создание резерва (один филиал) | 8 | 45–49 | 154–170 мс | 207–220 мс | ≤ 300 мс ✅ |
| Конкурентные бронирования | 40 одновременно | — | — | — | ≥ 20 попыток/с, без двойного бронирования ✅ |

**Оптимизация резерва (2026-11-21).** До неё было 24 резерва/с, p95 528 мс. Замер по шагам показал: блокировка филиала держалась около 30 мс, из них 9 мс уходило на загрузку каталога и расписаний, которая от блокировки не зависит. Теперь под блокировкой выполняются только занятость, проверки и вставки, около 15 мс (ARCHITECTURE §5.2). Каталог, расписания и акции загружаются до транзакции параллельно. Клиент и согласия создаются под блокировкой клиента, ответ читается после фиксации. Убраны два лишних запроса: инвалидация кодов новой записи и настройки организации для OTP. Гарантии не изменились: 40 параллельных попыток на один слот по-прежнему дают ровно 1 успех, все тесты проходят.

**Вывод.** Обе цели выполнены на одном процессе. Резервы одного филиала по-прежнему сериализуются, разных филиалов — выполняются параллельно. Показатели нужно подтвердить на согласованной инфраструктуре (ТЗ §23) с несколькими экземплярами API. Если понадобится больше 45 резервов в секунду на один филиал, следующий шаг — блокировать набор затрагиваемых ресурсов вместо филиала.
