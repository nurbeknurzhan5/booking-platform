# Решения и вопросы на согласование

ТЗ §30.3 запрещает придумывать бизнес-правила. Там, где ТЗ неоднозначно, ниже предложен конкретный вариант. Он реализован как **настройка или легко изменяемое правило** и ждёт подтверждения заказчика.

Статусы: ✅ утверждено · 🟡 предложено, реализовано, ждёт подтверждения · 🔴 нужен ответ или доступ заказчика.

Для обезличивания триггер разрешает только `UPDATE` полей с ПД — before/after в `audit_logs`, phone/ip в `client_consents` — и только в транзакции с `SET LOCAL app.pii_erasure = on` (миграция `20261125000000_pii_erasure`); `DELETE` запрещён всегда. Что остаётся после обезличивания и почему — SECURITY.md | Журналы сохраняют доказательную силу, ПД удаляются по запросу |
| D-46 | Допустимые даты | Даты (`YYYY-MM-DD`) и ISO-моменты принимаются только с годами 1900–2999 и только существующие (2026-02-31, 2026-13-01, 2025-02-29 → `400 VALIDATION_ERROR`). Периоды (подписка, акции, подписка при создании организации) сравниваются как моменты времени с учётом смещения, а не как строки | Без «сдвига» несуществующей даты на следующий месяц и ошибок 500 |
| D-47 | Ссылка в сообщении о переносе | Гость, перенёсший запись по ссылке управления, получает ту же ссылку (в outbox она зашифрована). При переносе из кабинета клиента или администратором — ссылка на `/cabinet`: токен управления хранится только хэшем, восстановить его нельзя; прежняя ссылка гостя продолжает действовать, ротации нет | Новая ссылка при каждом переносе потребовала бы рассылать её и гасить старую |
| D-48 | Повтор зашифрованных сообщений из DLQ | Вручную повторить из DLQ можно только подтверждение и перенос записи (`RETRYABLE_SENSITIVE_TYPES`: `appointment_confirmed`, `appointment_rescheduled`): их параметры остаются зашифрованными. У одноразовых секретов (OTP, ссылка подтверждения, предложение листа ожидания) параметры в DLQ стираются, повтор недоступен — клиент запрашивает новый код или ссылку | Устаревший одноразовый секрет не уходит повторно |
| D-49 | Область ключей идемпотентности | Область ключа для переноса, отмены и смены статуса включает действующее лицо: `guest:<sha256(токена)>`, `client:<userId>`, `staff:<userId>`. Ключ «в работе» старше 10 минут с тем же телом считается брошенным и выполняется заново; ключ старше 48 часов свободен; сбой записи ответа не превращает успешное действие в ошибку | Один ключ у разных людей не пересекается |
| D-50 | Запросы внутри транзакции | Запросы внутри транзакции Prisma выполняются последовательно (обёртка адаптера pg): pg@9 перестанет принимать параллельные запросы на одном соединении (сейчас — `DeprecationWarning`) | Без изменения стека; параллельность сохраняется вне транзакций |
| D-51 | Публичный `/health` | Статистика очереди уведомлений (`notifications`) в публичном `/health` кешируется на 30 с; доступность БД проверяется на каждый запрос | Частые проверки не нагружают БД подсчётом outbox |
| D-52 | Непроверенный номер сотрудника | Если номер указан сотруднику без подтверждения, а клиент подтверждает этот номер кодом, номер освобождается в пользу клиента: создаётся отдельный клиентский профиль, номер снимается с профиля сотрудника (аудит `user.unverified_phone_released`). Записи по номеру видит только тот, кто его подтвердил | Номер нельзя «присвоить», указав его в профиле |
| D-53 | Swagger и CSP API | Swagger UI и `docs-json` в production (`APP_ENV=production`) не публикуются, описание API — `docs/openapi.json`. CSP API строгая (`default-src 'none'; frame-ancestors 'none'`), `'unsafe-inline'` — только для страницы Swagger вне production | Меньше поверхности атаки в production |
| D-54 | Прокси, IP клиента и журналы веб-сервера | Next.js (rewrite `/api/*`) присланный клиентом `X-Forwarded-For` пропускает как есть и своей записи не добавляет, а адрес соединения в Next.js 16 (proxy/middleware) недоступен — нормализовать заголовок на стороне сайта нельзя. Поэтому `TRUST_PROXY` = число прокси перед Next.js, которые **перезаписывают** `X-Forwarded-For`: production за Caddy (без `trusted_proxies` перезаписывает адресом соединения) — `1`; локально, CI/E2E и Codespaces (перед Next.js такого прокси нет или его поведение не гарантировано) — `0`: заголовок игнорируется, IP = адрес соединения от Next.js, лимиты по IP общие для всего стенда. Значение по умолчанию в конфигурации — `0` (fail-closed). Дополнительно API доверяет не больше `TRUST_PROXY` адресам и только из внутренних сетей. В журнале Caddy токены в адресе и query маскируются, учётные заголовки не пишутся (`format filter`) | Подставленный клиентом `X-Forwarded-For` не обходит rate limit ни через сайт, ни напрямую; токены не попадают в журналы. Цена: на тестовых стендах один IP-лимит на всех посетителей |
| D-55 | Ошибки тела запроса | Ошибки body-parser переводятся в формат API до обработки Nest (иначе Nest отдаёт текст парсера или 500): тело JSON больше 1 МБ → 413 `PAYLOAD_TOO_LARGE`, битый JSON → 400 `VALIDATION_ERROR` «Некорректный JSON в теле запроса», неподдерживаемые `Content-Encoding`/`charset` → 415 `UNSUPPORTED_MEDIA_TYPE`, оборванное тело → 400. В журнал — уровень warn без стека | Ошибки клиента не выглядят как сбои сервера и не засоряют журнал |
