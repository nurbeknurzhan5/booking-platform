# Архитектура платформы онлайн-записи

Версия 1.0 · основание: ТЗ 4.0 · статус: стек утверждён заказчиком 2026-11-19.

## 1. Утверждённый стек

| Слой | Технология | Обоснование |
|---|---|---|
| Frontend | Next.js (App Router) + React + TypeScript strict + Tailwind CSS | рекомендация ТЗ §19.1, SSR для публичных страниц |
| Backend | NestJS + TypeScript strict | рекомендация ТЗ, модульность, DI, guards |
| БД | PostgreSQL 17 | ТЗ §20; exclusion constraints (`btree_gist`) против двойного бронирования |
| ORM | Prisma 7 (+ ручные SQL-миграции для ограничений, которые Prisma не описывает) | рекомендация ТЗ |
| Очереди / фоновые задачи | PostgreSQL: таблицы outbox/jobs + `FOR UPDATE SKIP LOCKED` + advisory locks | утверждено вместо Redis: меньше инфраструктуры, транзакционный outbox в той же БД |
| Rate limiting | PostgreSQL (таблица счётчиков с атомарным upsert) | без Redis; достаточен для 100 RPS |
| Валидация / контракты | Zod (общие схемы в `packages/shared`) + nestjs-zod → OpenAPI | единые типы frontend/backend |
| API | REST `/api/v1`, OpenAPI (Swagger UI `/api/docs`) | ТЗ §21 |
| Файлы | S3-совместимое объектное хранилище (prod), локальный диск (dev); `sharp` для обработки | ТЗ §24 |
| Тесты | Jest + SWC (unit/integration API), Playwright (E2E), собственный нагрузочный скрипт | ТЗ §26 |
| Контейнеры | Docker (multi-stage), docker-compose для production | ТЗ §27 |

Redis в MVP не используется. Если нагрузка вырастет, его можно подключить за интерфейсами `RateLimitStore` и `JobQueue`, переписывать бизнес-логику не придётся.

## 2. Модульный монолит

```
apps/
  api/        NestJS: HTTP API (процесс api) + фоновый воркер (процесс worker), общий код
  web/        Next.js: публичные страницы филиалов, кабинеты клиента/админа/владельца/суперадмина
packages/
  shared/     Zod-схемы контрактов API, перечисления (статусы, роли, права), чистые функции
infra/        Dockerfile'ы, docker-compose.prod.yml, скрипты резервного копирования
docs/         документация
```

Один репозиторий и одна кодовая база API, но два процесса:

- **api**: обрабатывает HTTP-запросы и ничего не отправляет во внешние сервисы синхронно;
- **worker**: отправляет уведомления из outbox, освобождает истёкшие резервы, пересчитывает статусы подписок, ставит напоминания, агрегирует аналитику, выполняет автоперевод.

Так выполняется требование ТЗ §15.2 «отправку сообщений выполнять через отдельный сервис», и при этом не появляются микросервисы (§19.1).

### 2.1. Слои внутри API

```
controller (HTTP, валидация Zod, OpenAPI)
   → guards (аутентификация, tenant context, RBAC, подписка)
   → service (бизнес-логика, транзакции)
   → Prisma (доступ к данным) / raw SQL для критичных участков
integrations/ (WhatsApp, SMS, перевод, хранилище) — только через интерфейсы, вызываются воркером
```

Модули API: `auth`, `users`, `organizations`, `branches`, `subscriptions` (+ `plans`), `services`, `specialists`, `resources`, `schedules`, `availability`, `appointments`, `clients`, `reviews`, `promotions`, `public-pages`, `templates`, `notifications`, `analytics`, `admin`, `integrations`, `files`, `audit`.

## 3. Мульти-тенантность и изоляция

1. Каждая таблица, принадлежащая организации, содержит `organization_id NOT NULL`, а таблицы уровня филиала содержат ещё и `branch_id`.
2. Важные связи сделаны **составными внешними ключами** `(organization_id, X_id) → X(organization_id, id)`. Например, запись нельзя привязать к услуге другой организации даже прямым SQL.
3. Tenant context определяется только на сервере: из сессии пользователя и его членства в организации (`user_organization_roles`). `organizationId` из URL проверяется на совпадение с членством; подмена ID даёт 404 (не 403, чтобы не раскрывать существование ресурса).
4. Все запросы к данным организации проходят через сервисы, которые обязательно принимают `TenantContext` и добавляют `organization_id` в `WHERE`.
5. Публичные endpoint'ы работают по постоянному `slug` филиала и сами определяют организацию.
6. Интеграционные тесты изоляции (ТЗ §26.5) проверяют каждую группу API: пользователь организации A не может прочитать или изменить данные организации B.

## 4. Аутентификация и авторизация

- **Сотрудники** (SUPERADMIN, OWNER, BRANCH_ADMIN) входят по email и паролю (argon2id). Первичные пароли выдаёт суперадмин или владелец, при первом входе пароль обязательно меняется.
- **Суперадмин**: обязательная MFA (TOTP). Для критических действий (блокировка организации, изменение подписки, отключение страницы, управление пользователями) нужен повторный TOTP-код (step-up, заголовок `X-MFA-Code`).
- **Клиенты** входят по номеру телефона и OTP. Телефон является основным идентификатором (E.164, проверка формата Казахстана `+7 7xx`).
- **Сессии**: непрозрачный случайный токен в cookie `HttpOnly; Secure; SameSite=Lax`, в БД хранится только SHA-256 токена (`user_sessions`). Есть отзыв сессий, TTL и скользящее продление.
- **CSRF**: double-submit токен (cookie `csrf_token` + заголовок `X-CSRF-Token`) для всех изменяющих запросов с cookie-сессией.
- **RBAC**: роли → права (`role_permissions`). Для BRANCH_ADMIN дополнительно есть доступ к конкретным филиалам (`user_branch_access`) и набор прав по каждому филиалу (`user_branch_permissions`), который выдаёт владелец. Проверка выполняется декоратором `@RequirePermission('appointments.manage')` и guard'ом, учитывающим филиал из запроса.

## 5. Ядро бронирования

### 5.1. Универсальная модель ресурсов
Всё, что можно занять, является **ресурсом** (`resources`): специалист, кабинет, зал, оборудование, автомобиль, пост, другое. У специалиста есть дополнительный профиль (`specialists`, связь 1:1 с ресурсом). Новые типы ресурсов добавляются значением справочника, без изменения архитектуры (ТЗ §1.1).

Требования услуги к ресурсам (`service_resources`): «нужен 1 ресурс типа `cabinet`, поддерживающий эту услугу». Требование к специалисту задаётся флагом `requires_specialist` и связью `specialist_services`.

### 5.2. Защита от двойного бронирования
Каждое занятие ресурса записывается строкой `appointment_resources (resource_id, start_at, end_at, is_active)`. На таблице действует ограничение PostgreSQL:

```sql
EXCLUDE USING gist (resource_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&) WHERE (is_active)
```

Никакие две активные брони одного ресурса не могут пересекаться **на уровне БД**, независимо от количества параллельных запросов и экземпляров API. Создание резерва выглядит так: одна транзакция → освобождение истёкших резервов затрагиваемых ресурсов → вставка всех строк ресурсов визита. Нарушение ограничения (`23P01`) превращается в ответ `409 SLOT_UNAVAILABLE`. Проверка и резерв составляют одну атомарную операцию (ТЗ §8.4), назначение всех ресурсов тоже атомарно (§6.1).

В интервал занятости входят буферы: `[start − buffer_before, end + buffer_after)`.

### 5.3. Расчёт слотов
1. Загружаются данные филиала на дату (в его часовом поясе): часы работы, исключения, перерывы, расписания ресурсов, активные брони.
2. Кандидаты на время начала генерируются с шагом `slot_interval` в пределах рабочего времени, с учётом минимального срока до записи и горизонта.
3. Для каждого кандидата детерминированный поиск с возвратом назначает каждой услуге визита специалиста (конкретного или «любого») и требуемые ресурсы. В последовательном режиме услуги идут одна за другой, в параллельном выполняются одновременно разными исполнителями.
4. При автоподборе кандидаты сортируются по загрузке за день (если включена равномерность), затем по `sort_order` и `id`. Порядок детерминирован.
5. Слот показывается, только если найдено полное назначение всех обязательных ресурсов (§7).

### 5.4. Статусы и переходы
```
pending_otp → confirmed | expired_otp | cancelled_by_client
confirmed   → completed | no_show | cancelled_by_client | cancelled_by_admin
```
Переходы описаны таблицей в `packages/shared` и проверяются только на сервере. Каждый переход записывается в `appointment_status_history`. Ручная запись администратором создаётся сразу в `confirmed` (без OTP). Перенос не меняет статус: он записывается в историю (`appointment_reschedules`) атомарной заменой строк ресурсов. При конфликте транзакция откатывается и старая запись остаётся нетронутой.

### 5.5. Временный резерв
`pending_otp` с `hold_expires_at` (по умолчанию 5 минут, настраивается). Освобождением занимается воркер (раз в 15 секунд, `SKIP LOCKED`). Дополнительно истёкшие резервы освобождаются внутри транзакции бронирования, поэтому слот становится доступен даже при задержке воркера.

### 5.6. Идемпотентность
Заголовок `Idempotency-Key` для создания резерва, подтверждения OTP, переноса, отмены и ручного создания записи. Таблица `idempotency_keys` хранит хэш запроса и ответ; повтор возвращает сохранённый ответ, а другой запрос с тем же ключом получает `422`.

## 6. Уведомления (Outbox)

1. Бизнес-операция в **той же транзакции** создаёт `notification_events` (уникальный `dedupe_key`, например `appointment:{id}:confirmed`) и строки `notification_outbox`: одна на канал и получателя, тоже с уникальным ключом.
2. Повторная обработка события упирается в уникальный ключ, поэтому дубль не создаётся (§15.2, критерий приёмки 17).
3. Воркер забирает сообщения через `FOR UPDATE SKIP LOCKED`, отправляет через адаптер канала и пишет попытку в `notification_attempts`. Повторы идут с экспоненциальной задержкой, после `max_attempts` сообщение получает статус `dead` (dead-letter queue, виден суперадмину, есть ручной повтор).
4. Каналы: WhatsApp Business Platform (официальный Cloud API Meta, только одобренные шаблоны), SMS (подключаемый адаптер), email (интерфейс на будущее). В dev/test дополнительно есть канал `dev_inbox`: сообщения пишутся в БД, и так тест получает OTP (§26.3). В production этот канал запрещён конфигурацией.
5. Webhook WhatsApp проверяет подпись `X-Hub-Signature-256` и обновляет `whatsapp_message_statuses`.
6. Бронирование никогда не ждёт внешний сервис.

## 7. Публичные страницы

- Постоянный URL: `/{locale}/b/{slug}`. Slug задаётся при создании филиала и не зависит от шаблона.
- Контент страницы (`page_drafts.content`, JSON с разделами) отделён от шаблона (`template_id` + цветовая схема), поэтому смена шаблона не теряет контент.
- Публикация создаёт неизменяемый снимок `page_publications` (версия + контент + шаблон). Посетители видят только последнюю публикацию, история версий и восстановление работают через копирование снимка в черновик.
- Шаблоны реализованы как React-раскладки во frontend. Их конфигурация (порядок разделов, допустимые цветовые схемы, позиции кнопки записи) хранится в `page_template_versions` и управляется суперадмином.
- Переводы хранятся в `page_translations` (сущность, поле, язык, текст, источник, статус: `missing` / `auto_translated` / `verified` / `manually_edited`, хэш исходного текста). Воркер переводит через адаптер (Google Cloud Translation, ключ предоставляет заказчик). Ручной перевод автоматически не перезаписывается.
- Доступность определяется функцией `resolvePublicAvailability(subscription, page)` по правилам §2.4 и возвращает причину недоступности.

## 8. Аналитика

События `analytics_events` (просмотр, клик по кнопке записи, начало оформления, успешная запись, отмена) с UTM-метками и referrer. Без cookies: идентификатор посетителя вычисляется как дневной хэш `(соль дня, IP, User-Agent, филиал)`, поэтому согласие на cookies не требуется. Боты отсекаются по User-Agent, внутренние просмотры (авторизованные сотрудники организации, предпросмотр) помечаются и исключаются. Агрегация по дням идёт в `analytics_daily_aggregates`. Правила описаны в [ANALYTICS.md](ANALYTICS.md).

## 9. Подписки

Эффективный статус вычисляется функцией `computeSubscriptionStatus(sub, now)`: `suspended` → иначе `active` (до `end_at`) → `grace_period` (до `end_at + grace_days`) → `expired`. Воркер раз в 5 минут сохраняет статус и пишет переходы в `subscription_history`. Guard `SubscriptionGuard` блокирует изменяющие операции владельцев и админов при `expired`/`suspended`; суперадмина он не ограничивает. Лимит филиалов проверяется в транзакции с блокировкой строки организации.

## 10. Время и локализация

- В БД всё время хранится в `timestamptz` (UTC). Часы работы хранятся как локальное время (`HH:MM`) плюс IANA-часовой пояс филиала (`Asia/Almaty` и т.д.), преобразования выполняет Luxon.
- Деньги хранятся целыми тенге (`integer`, KZT без тиын).
- Интерфейс кабинетов на русском и казахском, публичные страницы на русском, казахском и английском.

## 11. Безопасность (кратко, подробно в [SECURITY.md](SECURITY.md))

argon2id, OTP хранится только как HMAC-SHA256 с секретом, ограничены попытки и частота отправки (по номеру, по IP, глобально), есть honeypot и проверка времени заполнения формы против ботов, helmet (CSP), Zod-валидация всех входов, Prisma и параметризованный SQL против инъекций, React-экранирование и санитизация текстов против XSS, CSRF-токены, проверка файлов по сигнатуре с перекодированием в WebP, аудит критических действий, MFA суперадмина, секреты только в переменных окружения, токены интеграций шифруются в БД (AES-256-GCM).
