# ТЕХНИЧЕСКОЕ ЗАДАНИЕ 4.0
## Универсальная SaaS-платформа онлайн-записи для сервисного бизнеса

Страна запуска Республика Казахстан  
Валюта KZT (тенге)  
Языки интерфейса русский и казахский  
Языки публичных страниц русский, казахский, английский  
Тип продукта Multi-tenant SaaS  
Инструмент разработки Claude Code  
Версия документа 4.0  
Назначение разработка MVP с последующим расширением до коммерческой платформы.

---

# 1. ЦЕЛЬ ПРОЕКТА

Разработать универсальную облачную платформу онлайн-записи для организаций, оказывающих услуги населению и бизнесу.

Платформа должна позволять организациям управлять филиалами, услугами, специалистами, оборудованием, расписанием, клиентами и записями.

Каждый филиал должен иметь собственную публичную страницу с постоянной ссылкой, каталогом услуг, информацией о специалистах и возможностью онлайн-записи.

Платформа должна работать по модели SaaS разные организации используют одну систему, но данные каждой организации полностью изолированы.

## 1.1. Поддерживаемые направления бизнеса

Система должна быть универсальной и поддерживать

- салоны красоты;
- барбершопы;
- массажные кабинеты;
- косметологические центры;
- оздоровительные центры;
- бани и сауны;
- автомойки;
- детейлинг-центры;
- автосервисы;
- другие сервисные организации.

Необходимо предусмотреть возможность добавления новых направлений без изменения основной архитектуры.

## 1.2. География и локализация

На первом этапе
- Республика Казахстан;
- валюта KZT;
- часовые пояса филиалов;
- интерфейс RUKK;
- публичные страницы RUKKEN;
- телефонные номера Казахстана;
- локальные форматы дат и времени.

Все даты и время в базе данных должны храниться в согласованном формате UTC с корректным преобразованием в часовой пояс филиала.

# 2. БИЗНЕС-МОДЕЛЬ SAAS

## 2.1. Принцип работы

Платформа является единой системой для множества организаций.

Каждая организация имеет
- собственный профиль;
- одного или нескольких владельцевадминистраторов;
- один или несколько филиалов;
- собственных клиентов;
- услуги;
- специалистов;
- ресурсы;
- расписания;
- записи;
- настройки;
- публичные страницы.

Данные одной организации не должны быть доступны другой организации.

## 2.2. Создание организаций

Публичная регистрация организаций отсутствует.

Создавать организации может только суперадминистратор.

Суперадминистратор должен иметь возможность
- создать организацию;
- указать название;
- указать направление деятельности;
- добавить контактные данные;
- создать филиалы;
- назначить владельца;
- создать администраторов;
- установить тариф;
- указать количество разрешённых филиалов;
- установить стоимость подписки;
- установить дату начала и окончания;
- внести информацию об оплате;
- продлить подписку;
- временно заблокировать организацию;
- восстановить доступ.

## 2.3. Подписки

Оплата в MVP производится вне платформы.

Клиент платит непосредственно организации платформы. Суперадминистратор вручную фиксирует поступление денег и активирует подписку.

Подписка должна содержать
- тариф;
- количество разрешённых филиалов;
- стоимость;
- дату начала;
- дату окончания;
- дату оплаты;
- сумму оплаты;
- историю продлений;
- льготный период;
- текущий статус.

Статусы

- `active` — активная подписка;
- `grace_period` — льготный период;
- `expired` — подписка закончилась;
- `suspended` — доступ приостановлен администратором.

После окончания подписки организация переходит в льготный период, если он предусмотрен настройками.

После завершения льготного периода
- публичные страницы скрываются;
- онлайн-запись отключается;
- клиенты не могут создавать новые записи;
- данные организации сохраняются;
- владельцы теряют возможность пользоваться платными функциями управления;
- суперадминистратор сохраняет административный доступ.

После подтверждения оплаты суперадминистратор восстанавливает подписку.

История платежей и продлений не удаляется.

## 2.4. Статус публичной страницы

Статусы

- `active`;
- `temporarily_closed`;
- `disabled`.

Правила
- `active` — страница доступна, запись разрешена;
- `temporarily_closed` — отображается оформленная страница «Временно закрыто», контакты доступны, запись отключена;
- `disabled` — страница полностью недоступна посетителям.

Статус подписки и статус страницы должны храниться отдельно.

Итоговая доступность определяется системным правилом

1. При `suspended` публичная запись отключена.
2. При `expired` после льготного периода страница скрыта.
3. При `temporarily_closed` страница показывает информацию о временном закрытии.
4. При `disabled` страница недоступна.
5. Только при активной подписке и статусе страницы `active` можно создать запись.

Необходимо сохранять причину недоступности страницы для корректного отображения посетителю.

# 3. РОЛИ И ПРАВА ДОСТУПА

Система должна поддерживать следующие роли.

## 3.1. Клиент — CLIENT

Может
- просматривать публичные страницы;
- просматривать услуги;
- просматривать специалистов;
- смотреть свободные слоты;
- создавать запись;
- подтверждать номер телефона через OTP;
- просматривать свои записи;
- переносить запись;
- отменять запись;
- оставлять отзыв;
- редактировать собственные контактные данные;
- получать уведомления.

Клиент может записываться с регистрацией или без регистрации.

## 3.2. Администратор филиала — BRANCH_ADMIN

Может
- управлять записями своего филиала;
- создавать записи вручную;
- просматривать клиентов;
- управлять расписанием в пределах выданных прав;
- управлять услугами и специалистами в пределах выданных прав;
- управлять ресурсами;
- подтверждать выполнение услуг;
- отменять записи;
- просматривать статистику филиала.

Доступ должен ограничиваться назначенными филиалами и разрешениями.

## 3.3. Владелец организации — OWNER

Может
- управлять организацией;
- создавать и редактировать филиалы в пределах тарифа;
- назначать администраторов;
- выдавать и отзывать права;
- управлять услугами;
- управлять специалистами;
- управлять ресурсами;
- управлять расписаниями;
- настраивать правила бронирования;
- редактировать публичные страницы;
- выбирать шаблоны;
- просматривать аналитику;
- управлять промокодами;
- настраивать уведомления;
- просматривать историю действий.

Владелец не может самостоятельно менять статус подписки или обходить ограничения тарифа.

## 3.4. Суперадминистратор — SUPERADMIN

Имеет полный системный доступ.

Может
- создавать организации;
- управлять подписками;
- управлять тарифами;
- устанавливать ограничения;
- создавать владельцев;
- управлять пользователями;
- блокировать организации;
- управлять каталогом шаблонов;
- модерировать публичный контент;
- просматривать системную аналитику;
- просматривать журнал действий;
- управлять системными настройками;
- контролировать интеграции;
- просматривать ошибки уведомлений;
- восстанавливать доступ.

Все критические действия суперадминистратора должны фиксироваться в журнале аудита.

## 3.5. Разграничение доступа

Использовать RBAC с дополнительным ограничением по организации и филиалу.

Запрещено
- получать данные другой организации;
- менять идентификаторы организации для обхода доступа;
- просматривать чужие записи;
- изменять чужие настройки;
- обходить ограничения тарифа через API.

Проверка прав выполняется на сервере, а не только на frontend.

Иерархия

Платформа → Организация → Филиалы → Услуги  Специалисты  Ресурсы  Записи.

У каждой организации может быть несколько филиалов.

Количество филиалов ограничивается подпиской.

Каждый филиал имеет
- название;
- адрес;
- телефон;
- график работы;
- часовой пояс;
- фотографии;
- описание;
- логотип или общую идентификацию;
- публичную страницу;
- отдельную постоянную ссылку;
- список услуг;
- список специалистов;
- список ресурсов;
- настройки записи.

Специалисты в разных филиалах должны иметь отдельные карточки и настройки, даже если принадлежат одному сотруднику организации.

# 5. УПРАВЛЕНИЕ УСЛУГАМИ

Владелец и уполномоченный администратор могут создавать услуги.

Поля услуги
- название;
- описание;
- категория;
- фотография;
- стоимость;
- продолжительность;
- буфер до услуги;
- буфер после услуги;
- доступные филиалы;
- доступные специалисты;
- необходимые ресурсы;
- статус активности;
- порядок отображения;
- возможность онлайн-записи.

Продолжительность указывается в минутах.

Стоимость хранится в KZT.

Необходимо поддерживать
- фиксированную цену;
- разные цены по филиалам;
- разные цены по специалистам, если разрешено настройками;
- временные акции;
- промокоды.

Цена и название услуги фиксируются в snapshot при создании записи.

Последующее изменение цены не должно менять уже созданные записи.

# 6. СПЕЦИАЛИСТЫ И РЕСУРСЫ

Система должна поддерживать универсальную модель ресурсов.

Типы ресурсов
- специалисты;
- кабинеты;
- залы;
- оборудование;
- автомобили;
- посты обслуживания;
- другие ресурсы.

Каждый ресурс имеет
- название;
- тип;
- филиал;
- описание;
- рабочий график;
- перерывы;
- доступность;
- статус;
- список поддерживаемых услуг.

Специалист дополнительно имеет
- имя;
- фотографию;
- описание;
- специализацию;
- список услуг;
- график работы;
- выходные;
- перерывы;
- статус активности.

## 6.1. Назначение ресурсов

Для услуги могут требоваться один или несколько ресурсов.

Система должна поддерживать
- одного специалиста на все услуги визита;
- разных специалистов на разные услуги;
- последовательное выполнение услуг;
- параллельное выполнение услуг.

Назначение всех необходимых ресурсов должно выполняться атомарно.

Нельзя допускать двойное бронирование
- специалиста;
- кабинета;
- оборудования;
- автомобиля;
- поста;
- любого другого ресурса.

Для параллельных операций использовать транзакции базы данных и механизмы блокировкиограничений целостности.

# 7. РАСПИСАНИЯ

Для каждого филиала задаётся
- рабочее время;
- выходные дни;
- праздничные дни;
- исключения;
- временное закрытие.

Для специалистов и ресурсов задаётся отдельное расписание.

Необходимо учитывать
- длительность услуги;
- буфер до и после услуги;
- рабочее время филиала;
- график специалиста;
- график ресурсов;
- уже существующие записи;
- временные резервы;
- настройки интервалов записи.

Нельзя показывать клиенту слоты, в которых отсутствует хотя бы один обязательный ресурс.

Система должна учитывать часовой пояс филиала.

# 8. СИСТЕМА ОНЛАЙН-ЗАПИСИ

Это один из основных модулей платформы.

## 8.1. Сценарий записи

1. Клиент открывает публичную страницу филиала.
2. Выбирает одну или несколько услуг.
3. Выбирает дату.
4. Выбирает специалиста или автоматический подбор.
5. Система показывает доступные слоты.
6. Клиент выбирает время.
7. Указывает имя и номер телефона.
8. Система создаёт временный резерв.
9. Отправляется OTP.
10. Клиент вводит OTP.
11. Система проверяет код.
12. Запись получает статус `confirmed`.
13. Клиент получает подтверждение.

## 8.2. Статусы записи

- `pending_otp`;
- `confirmed`;
- `completed`;
- `no_show`;
- `cancelled_by_client`;
- `cancelled_by_admin`;
- `expired_otp`.

Разрешённые переходы должны быть реализованы через серверную бизнес-логику.

`pending_otp` — временный резерв, ожидающий подтверждения телефона.

`confirmed` — подтверждённая запись.

`completed` — услуга выполнена.

`no_show` — клиент не пришёл.

`cancelled_by_client` — отменена клиентом.

`cancelled_by_admin` — отменена администратором.

`expired_otp` — срок подтверждения истёк.

История изменения статусов должна сохраняться.

## 8.3. Временный резерв

После выбора времени создаётся резерв на 5 минут.

Владелец может настроить
- продолжительность резерва;
- возможность продления;
- максимальное количество активных записей клиента;
- правила повторной записи;
- ограничения по номеру телефона.

Если клиент не подтвердил OTP за установленное время
- резерв освобождается;
- запись получает статус `expired_otp`;
- слот снова становится доступным.

Освобождение должно выполняться надёжным фоновым процессом.

## 8.4. Конкурентная запись

Если два клиента одновременно пытаются занять один слот

- первый успешно получает временный резерв;
- второй получает сообщение, что время уже недоступно;
- второй должен выбрать другой слот.

Запрещено допускать двойное бронирование даже при высокой нагрузке.

Проверка доступности и создание резерва должны быть одной атомарной операцией.

## 8.5. Перенос записи

Клиент может самостоятельно переносить запись до дедлайна, установленного владельцем.

Правила
- повторный OTP не требуется;
- клиент может выбрать другого свободного специалиста;
- старый слот сохраняется, пока новый не подтверждён системой;
- если новый слот занят, старая запись остаётся без изменений;
- перенос выполняется атомарно;
- история переноса сохраняется.

При переносе система должна повторно проверить все необходимые ресурсы.

## 8.6. Отмена записи

Владелец устанавливает срок, до которого клиент может отменить запись.

После установленного срока отмена клиентом запрещается, если владелец не разрешил исключения.

Администратор может отменять записи с указанием причины.

## 8.7. Несколько услуг в одном визите

Клиент может выбрать несколько услуг.

Система должна
- рассчитать общую продолжительность;
- рассчитать общую стоимость;
- определить последовательность или параллельность;
- назначить необходимые ресурсы;
- показать итоговое время;
- создать связанную группу услуг одного визита.

У каждой услуги внутри визита должен быть собственный исполнитель и ресурсный набор, если это предусмотрено режимом организации.

## 8.8. Автоматический подбор специалиста

Клиент может
- выбрать конкретного специалиста;
- выбрать любого свободного специалиста.

При автоматическом подборе система выбирает доступного специалиста, который соответствует требованиям услуги и доступности ресурсов.

Алгоритм должен быть детерминированным и учитывать равномерность распределения нагрузки, если такая настройка включена.

## 8.9. Ограничения клиента

Владелец может настраивать
- максимальное количество активных записей на клиента;
- повторную запись при наличии активной;
- разрешение администратору создавать несколько записей на один номер;
- минимальный срок до записи;
- максимальный горизонт записи;
- дедлайн переноса;
- дедлайн отмены.

Все ограничения проверяются на сервере.

# 9. WAITLIST — ЛИСТ ОЖИДАНИЯ

Функция необязательна для первого запуска, но архитектурно должна быть предусмотрена.

Если подходящий слот освобождается
- система находит клиентов из листа ожидания;
- отправляет предложение первым трём подходящим клиентам одновременно;
- у предложения есть срок действия;
- первый успешно забронировавший слот получает его;
- остальные предложения аннулируются.

Владелец настраивает
- включение функции;
- срок действия предложения;
- количество получателей;
- порядок приоритета;
- дальнейшие действия после истечения срока.

Нельзя допускать двойного назначения освобождённого слота.

# 10. OTP И АВТОРИЗАЦИЯ

Телефон является основным идентификатором клиента.

Поддержать
- регистрацию по номеру телефона;
- вход по номеру телефона;
- подтверждение номера через OTP;
- гостевую запись;
- привязку гостевых записей к аккаунту после подтверждения номера.

OTP
- действует 5 минут по умолчанию;
- имеет ограничение на количество попыток;
- имеет ограничение на частоту отправки;
- хранится в защищённом виде;
- не должен попадать в обычные логи;
- после успешной проверки становится недействительным.

Необходимо реализовать защиту от
- перебора кодов;
- массовой отправки OTP;
- автоматизированных запросов;
- подмены номера;
- повторного использования кода.

Гостевые записи после подтверждения номера должны связываться с профилем клиента.

При объединении дублей необходимо сохранять историю записей и аудит изменений.

# 13. ПУБЛИЧНАЯ СТРАНИЦА ФИЛИАЛА

Каждый филиал имеет собственную постоянную публичную ссылку.

Ссылка не меняется при смене шаблона.

Публичная страница — это одностраничная страница филиала, а не полноценный многостраничный сайт.

## 13.1. Состав страницы

- логотип;
- название;
- описание;
- основные фотографии;
- услуги;
- специалисты;
- график работы;
- адрес;
- контакты;
- карта;
- отзывы;
- акции;
- кнопка онлайн-записи;
- ссылки на социальные сети и мессенджеры.

## 13.2. Редактирование страницы

Редактировать страницу могут
- владелец;
- назначенные им администраторы с соответствующими правами.

Редактирование доступно
- через личный кабинет;
- через кнопку «Редактировать страницу» при просмотре публичной страницы, если пользователь авторизован и имеет права.

## 13.3. Черновики и публикация

Изменения сначала сохраняются в черновике.

До нажатия кнопки «Опубликовать» посетители видят предыдущую опубликованную версию.

Необходимо реализовать
- сохранение черновика;
- предварительный просмотр;
- публикацию;
- историю версий;
- восстановление предыдущей версии.

## 13.4. Шаблоны

Платформа предоставляет каталог готовых профессиональных шаблонов.

Все организации имеют доступ к общему каталогу.

Суперадминистратор
- создаёт шаблоны;
- редактирует шаблоны;
- публикует шаблоны;
- отключает шаблоны;
- определяет доступный каталог.

Владелец
- выбирает шаблон;
- просматривает его на компьютере и телефоне;
- применяет его;
- бесплатно и неограниченно меняет шаблоны;
- возвращается к ранее использованным шаблонам.

При смене шаблона контент не должен теряться.

Владелец может менять
- логотип;
- фотографии;
- тексты;
- предусмотренные шаблоном цветовые схемы.

Произвольное изменение цветов и структуры дизайна не разрешается.

Порядок основных разделов определяется шаблоном.

Расположение кнопки записи может настраиваться владельцем в пределах предусмотренных шаблоном вариантов.

## 13.5. Мультиязычность

Публичная страница поддерживает
- русский;
- казахский;
- английский.

Владелец выбирает основной язык.

Если перевод отсутствует, система может автоматически перевести контент.

Посетитель должен видеть уведомление о том, что автоматический перевод может содержать неточности.

Владелец может редактировать перевод вручную.

Ручной перевод нельзя автоматически перезаписывать без согласия владельца.

Новое содержимое также должно попадать в очередь перевода.

Для каждого перевода необходимо хранить источник и статус
- отсутствует;
- автоматически переведён;
- проверен;
- отредактирован вручную.

## 13.6. Карта

Основной картографический сервис — 2GIS.

Владелец может включать или отключать карту.

Необходимо хранить
- адрес;
- координаты;
- ссылку на карту;
- настройки отображения.

При отсутствии технической возможности встроить карту следует показывать ссылку на открытие адреса в 2GIS.

## 13.7. Социальные сети

Владелец может добавлять ссылки на любые социальные сети и мессенджеры.

Для популярных сервисов система автоматически определяет платформу и отображает соответствующую иконку.

Для остальных ссылок владелец указывает собственное название.

## 13.8. Модерация

Владелец отвечает за размещаемый контент.

Суперадминистратор может модерировать публичные страницы, отключать недопустимый контент и фиксировать причины модерации.

# 23. ПРОИЗВОДИТЕЛЬНОСТЬ И НАДЁЖНОСТЬ

Начальная целевая аудитория
- 100–1 000 организаций;
- несколько филиалов у части организаций;
- одновременная работа пользователей из разных организаций.

Ориентиры для проектирования
- получение доступных слотов до 150 мс при целевой нагрузке;
- создание резерва до 300 мс при целевой нагрузке;
- базовая целевая нагрузка 100 RPS;
- целевая проверка конкурентных бронирований не менее 20 попыток в секунду.

Это целевые показатели, а не гарантированные характеристики.

Необходимо подтвердить их нагрузочным тестированием на согласованной инфраструктуре.

Система должна
- корректно обрабатывать временную недоступность внешних сервисов;
- повторять безопасные операции;
- не терять события;
- предотвращать дублирование;
- иметь централизованный мониторинг;
- поддерживать резервное копирование;
- иметь процедуру восстановления.

Для MVP установить и документировать целевые RPO и RTO после выбора инфраструктуры.

# 26. ТЕСТИРОВАНИЕ

## 26.3. E2E-тесты

Проверить полный сценарий клиента

1. Открыть публичную страницу.
2. Выбрать услугу.
3. Выбрать специалиста.
4. Выбрать дату и время.
5. Ввести номер телефона.
6. Получить OTP в тестовой среде.
7. Подтвердить номер.
8. Получить подтверждённую запись.
9. Перенести запись.
10. Отменить запись.

## 26.4. Конкурентные тесты

Обязательно проверить
- два клиента бронируют один слот;
- два клиента одновременно выбирают одного специалиста;
- два клиента используют один кабинет;
- параллельное назначение ресурсов;
- истечение OTP;
- перенос на занятый слот;
- повторный запрос создания записи;
- повторная доставка уведомления.

Результат должен исключать двойное бронирование.

## 26.5. Проверки безопасности

Проверить
- доступ к чужой организации;
- доступ к чужому филиалу;
- подмену ID;
- повышение привилегий;
- перебор OTP;
- массовые запросы;
- загрузку запрещённых файлов;
- доступ к административным endpoint.

# 29. КРИТЕРИИ ПРИЁМКИ

Продукт нельзя считать готовым только потому, что интерфейс отображается и код успешно собирается.

Обязательные критерии

1. Организации изолированы друг от друга.
2. Роли и права работают на сервере.
3. Суперадминистратор может создать организацию и активировать подписку.
4. Владелец может настроить филиал.
5. Можно создавать услуги, специалистов и ресурсы.
6. Расписание корректно рассчитывает доступность.
7. Клиент может создать запись.
8. OTP работает с ограничениями.
9. Нельзя забронировать один ресурс дважды.
10. Перенос не уничтожает старую запись при неудаче.
11. Цена записи сохраняется в snapshot.
12. Публичная страница доступна по постоянной ссылке.
13. Смена шаблона не уничтожает контент.
14. Черновик не публикуется автоматически.
15. Подписка корректно ограничивает доступ.
16. WhatsApp использует официальный API.
17. Уведомления не дублируются при повторной обработке событий.
18. Аналитика учитывает UTM.
19. Пройдены тесты доступа и изоляции.
20. Есть резервное копирование и инструкция восстановления.
21. Нет критических ошибок, блокирующих основные пользовательские сценарии.
22. Есть документация по запуску и обслуживанию.

# 30. ПРАВИЛА РАБОТЫ CLAUDE CODE

Claude Code является основным инструментом разработки.

Он должен действовать как инженерная команда архитектор, backend-разработчик, frontend-разработчик, специалист по базам данных и тестировщик.

## 30.1. Основные правила

1. До начала разработки полностью прочитать это ТЗ.
2. Не начинать массовое написание кода до проектирования архитектуры.
3. Не пропускать обязательные требования.
4. Не придумывать бизнес-правила при наличии неоднозначности.
5. Не менять утверждённую архитектуру без согласования.
6. Не удалять уже работающий функционал без согласования.
7. Не использовать временные заглушки в production-функциях.
8. Не оставлять критические функции с фиктивной реализацией.
9. Не обходить безопасность ради скорости.
10. Не считать функцию готовой без тестов.
11. После каждого этапа обновлять документацию.
12. Все ошибки исправлять до перехода к следующему этапу.

## 30.2. Формат выполнения задач

Перед каждым этапом Claude Code должен сообщать

- что будет сделано;
- какие файлы будут созданы;
- какие изменения будут внесены в базу данных;
- какие API будут добавлены;
- какие тесты будут выполнены;
- какие риски существуют.

После этапа сообщать

- что реализовано;
- какие тесты прошли;
- какие тесты не прошли;
- какие проблемы остались;
- что нужно согласовать;
- можно ли переходить дальше.

## 30.3. Работа с неизвестными требованиями

Если требование неоднозначно
- не выбирать случайное решение;
- проверить связанные разделы ТЗ;
- предложить конкретный вариант;
- объяснить последствия;
- запросить согласование, если решение влияет на бизнес-логику или архитектуру.

Нельзя самостоятельно менять бизнес-правила, согласованные заказчиком.

## 30.4. Качество кода

Обязательны
- TypeScript strict mode;
- единый стиль кода;
- линтер;
- форматирование;
- автоматические тесты;
- миграции;
- типизированные API;
- обработка ошибок;
- документация;
- отсутствие секретов в репозитории.

# 32. ИТОГОВЫЙ РЕЗУЛЬТАТ

Результатом разработки должна стать универсальная SaaS-платформа онлайн-записи, в которой

- суперадминистратор управляет организациями и подписками;
- владельцы управляют своими организациями;
- администраторы управляют назначенными филиалами;
- клиенты записываются онлайн;
- специалисты и ресурсы назначаются без конфликтов;
- каждый филиал имеет публичную страницу;
- организации используют готовые шаблоны;
- система отправляет уведомления;
- WhatsApp работает через официальный API;
- владельцы видят аналитику;
- персональные данные защищены;
- архитектура позволяет масштабировать проект.

Главный приоритет разработки надёжная система бронирования, корректная изоляция организаций, безопасность данных и стабильная работа основных пользовательских сценариев.

Конечная цель коммерчески пригодная SaaS-платформа для сервисного бизнеса в Казахстане с возможностью дальнейшего выхода на другие рынки.
